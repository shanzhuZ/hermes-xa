## 0. 一分钟读懂要做什么

当前问题：

1. Gateway 经 Java 已把思考 **SSE 中继**给前端，但前端若乱渲染多种事件会花屏 → **只拼 `assistant.delta` 的 content**。
2. 步骤树主要靠 **Python Hook 入库后**才变状态，慢于工具真实开始 → 树与思考不同步 → 用 **Java 在 `tool.started` 粗写 running**，Hook 继续写准业务终态（方案 **C**）。
3. 任务结束后刷新，思考区要可回放 → **只落库并渲染最终 `assistant.completed` 的 content**。
4. 任务**进行中**刷新 → 本阶段 **不做 partial 落库（I1）**；接受可能丢已出字。稳定后再做 I2。

本周**不做**：整体提速（慢于 Chat ~5x 的问题后置）、I2 partial、全事件时间线落库、把步骤状态机整迁到 Java（方案 A）。

## 3. 目标架构

```text
Gateway SSE
    │
    ▼
HermesGatewayClient.drainStream
    │
    ├─► ThoughtStreamHub.publishGatewayEvent     （前端 SSE，不变）
    │
    ├─► ThoughtFinalPersistence                  （本期新增）
    │       仅 assistant.completed → 落库 finalContent
    │
    └─► CoarseStepSync                           （本期新增）
            tool.started / tool.completed(白名单)
            → CollectTaskMapper.updateStepStatus（粗）

Python Hook（继续）
    └─► set_step_status + 子节点 + 业务 completed/failed/skipped（细，可覆盖粗）

前端
    ├─ 进行中：SSE 只拼 assistant.delta.content；tree 轮询看粗+细状态
    └─ 已完成：GET /thoughts → finalContent；可不依赖内存 SSE
```

### 3.1 冲突约定（方案 C，必须实现注释 + 遵守）

| 写入方 | 允许 | 禁止 |
|--------|------|------|
| Java `CoarseStepSync` | `pending`→`running`；对**可粗完成白名单**工具写 `completed`；粗 message 如「执行 {tool}」 | 创建/删除子步骤；改业务 payload；对 Apify/入库类工具写 `completed`；响应 `_thinking` / web_search / browser / firecrawl |
| Hook | 任意准确 `message`；`completed`/`failed`/`skipped`；子节点；fail-forward / reopen 等既有例外 | 无业务理由把已业务 `completed` 打回 `pending`（现有合法 reopen 保留并注明） |

预期 UI：可能短暂「先绿后红/后改文案」；可接受。Java 粗 `completed` 白名单**先从严**，宁可只标 running。

## 4. 数据与 API 设计

### 4.1 存储 `finalContent`（二选一，推荐 A）

**推荐 A — 对话表复用（少迁库）**

向 `hermes_user_dialogues` 插入/更新一条：

- `task_id`
- `session_id`（可从 `hermes_tasks` 查）
- `role = 'assistant'`
- `msg_type = 'thoughts_final'`（新类型；与现有 `summary` / `user_input` 区分）
- `content` = `assistant.completed` 的文本

若同一 task 多次 completed：先 `SELECT id ... WHERE msg_type='thoughts_final'`，有则 `UPDATE content`，无则 `INSERT`。

**备选 B — 任务表加列**

```sql
ALTER TABLE hermes_tasks
  ADD COLUMN thoughts_final MEDIUMTEXT NULL COMMENT 'assistant.completed 思考终稿' AFTER error_message;
```

若选 B，同步改 `CollectTaskMapper` 与文档 [`MySQL数据库设计.md`](MySQL数据库设计.md) / [`MySQL-01账号采集表设计.md`](MySQL-01账号采集表设计.md)。

**注意**：`TaskFinalAnswerQueryService` 查的是业务报告终稿，**不要**把 `thoughts_final` 混进该接口；独立 `GET /thoughts`。

### 4.2 新接口：`GET /api/tasks/{taskId}/thoughts`

响应 JSON 建议：

```json
{
  "taskId": "uuid",
  "taskStatus": "running|completed|failed|pending",
  "finalContent": "......或 null",
  "hasFinal": true,
  "streamAvailable": true,
  "thoughtsStreamUrl": "/api/tasks/{taskId}/thoughts/stream",
  "mode": "final|live"
}
```

规则：

- `taskStatus` 为终态（`completed` / `failed`，按项目现有判定）且有 `finalContent` → `mode=final`，前端只渲染 `finalContent`
- 否则 → `mode=live`，`finalContent` 多为 null（I1 不提供 partial）；前端连 SSE
- 任务不存在 → 404

可选：起任务 / `GET task` 响应增加 `"thoughtsUrl": "/api/tasks/{id}/thoughts"`（与已有 `thoughtsStreamUrl` 并列）。

### 4.3 现有流式接口约定（不改协议形状，只钉死语义）

`GET /api/tasks/{taskId}/thoughts/stream`

- 事件名与 payload 保持 `ThoughtEventNormalizer` + Hub 现状
- 前端**仍只拼** `eventType === "assistant.delta"` 的 `content`
- 完成态回放**不以 stream 为准**，以 `GET /thoughts` 的 `finalContent` 为准

## 5. Java 实现说明

### 5.1 建议新增类（包：`com.example.aw.collect.stream`）

保持 JDK8、少抽象：

1. **`ThoughtFinalStore`**（或 `ThoughtFinalPersistence`）  
   - 方法：`void saveAssistantCompleted(String taskId, String content)`  
   - 方法：`String findFinalContent(String taskId)`  
   - 空 content 忽略；异常打日志，**不要拖垮 SSE 转发**

2. **`CoarseStepSync`**  
   - 方法：`void onToolEvent(String taskId, String eventType, String toolName, Boolean success)`  
   - 内部查 `hermes_tasks.task_type`，查映射表  
   - 写库失败只打日志，不影响 Hub

3. **`CoarseToolStepMapping`**（可用静态表 / 内部 Map）  
   - 字段建议：`toolName` → `{ stepKey, allowCoarseComplete: boolean, ignore: boolean }`  
   - 或：`ignoreTools` 集合 + `runningMap` + `coarseCompleteWhitelist`

挂钩点（推荐）：在 `ThoughtStreamHub.publishGatewayEvent` **末尾**调用 Store + Sync，这样所有 Gateway 事件统一；或在 `HermesGatewayClient.drainStream` 里 `publishGatewayEvent` 之后。**优先 Hub 内一处挂钩**，避免漏事件。

伪逻辑：

```text
publishGatewayEvent(...):
  normalized = Normalizer.normalize(...)
  publish to SSE subscribers
  if event == assistant.completed:
      ThoughtFinalStore.save(content)
  if event starts with tool.:
      CoarseStepSync.onToolEvent(...)
  if terminal:
      complete channel
```

`assistant.completed` 是否算 terminal：现状 `isTerminal` **不含** `assistant.completed`（只含 done / run.completed / run.failed / error）——**保持不变**；completed 正文保存与 channel complete 解耦。
