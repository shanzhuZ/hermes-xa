## 二、根因分层（按重要性）

### 层 1：Skill 无法「执行」流程（架构）

- Skill / `collect-rules.yaml` 只是 **给 LLM 看的文档**，Hermes **不会在运行时拦截**：
  - `web_search` / `browser_navigate`
  - 英文输出
  - 跳过步骤 4～6 直接写报告
- 此前已删除 `collect-workflow` 门禁 MCP，**没有任何代码级步骤锁**。
- `config.yaml` → `platform_toolsets.cli` 仍包含 **`web`、`browser`**，失败时模型会启用这些工具（日志已证实）。

**结论**：继续加长 Skill **不能从根本解决**跳步和乱写报告；最多降低概率。

---

### 层 2：模型与全局配置（英文、调查报告体）

```yaml
# config.yaml
agent.personalities.helpful: You are a helpful, friendly AI assistant.  # 英文
model: Qwen2.5-VL-32B-Instruct  # 自定义端点
session_reset.mode: none  # 会话长期累积
```

- **无全局「必须简体中文」** 的系统约束；Skill 里写中文对 Qwen 是软提示。
- 模型在工具失败后倾向 **OSINT / Investigation Report** 英文模板（日志全文如此）。
- `session_reset: none` → 同一会话可能混入 **上一次别的账号任务**（Caitlin 与 whyyoutouzhele 无法从本次 Maigret 结果解释，高度怀疑 **会话上下文污染**）。

**结论**：英文 + 错账号 = **配置 + 会话 + 模型行为**，不是 Skill 漏写一条规则。

### 层 3：Apify — 并非「全挂」，而是 **调用方式错误**

日志中的典型错误：

```
tool_call mcp_apify_apify__instagram_scraper_get_dataset_items  # ❌ 不存在
```

正确契约（3 个**独立**工具）：

1. `mcp_apify_apify__instagram_scraper`（或 tiktok/telegram 等 Actor）
2. `mcp_apify_get_actor_run`（或 `get-actor-run`）
3. `mcp_apify_get_dataset_items`（**不要**拼在 Actor 名后面）

本地 `hermes mcp test apify`：MCP 连通正常，9 个工具；`.env` 中 `APIFY_TOKEN` 已配置。

日志里 Instagram/TikTok Actor **曾跑 13s / 27s**，说明 **Token 与 MCP 可用**；失败点在于：

- 部分调用 `-32602` = **入参 schema 不对**（如 Telegram 用了 `channelUrls` 而非 `channels`）
- dataset 用 **编造的工具名** 拉取 → 全部 error
- 个别平台 `not_found` 可能是 **账号确实不存在/私密**（需与工具错误区分）

**结论**：Apify「全失败」≈ **Agent 不会用三轮契约 + Skill 里工具名/示例误导**；不是 Apify MCP 未安装。

### 层 6：GBK `UnicodeDecodeError`

```
Thread-20 _readerthread ... UnicodeDecodeError: 'gbk'
```

- 来源：Windows 上 **Hermes 主进程读某子进程 stderr 默认 GBK**（常见于 Maigret 子进程）。
