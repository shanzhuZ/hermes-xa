# 05 · 账号核查报告

> **交互模式**：密塔 AI 深度模式 —— 在用户确认**报告类型、章节结构、详略程度、输出格式**后，汇总 01～04 阶段产物，生成可交付的账号核查报告。  
> **定位**：面向业务方 / 研判人员的**最终交付物**，强调证据可追溯、结论可解释。

---

## 一、业务目标

将采集、跨平台图谱、核查结论、多模态分析等结果，整合为一份**结构清晰、证据充分、可复核**的账号核查报告。

| 产出 | 说明 |
|------|------|
| 报告正文 | Markdown / HTML / PDF 可渲染结构 |
| 证据附录 | 工具输出摘要、关键截图索引 |
| 元数据 | 任务 ID、生成时间、版本、参与阶段 |
| 可选结构化 JSON | 供 Java / 前端系统消费 |

---

## 二、触发条件

- 完成 **03 账号核查** 或 **04 多模态分析** 后跳转
- 用户指令：「给这个账号出一份核查报告」
- 外部系统（Java）通过 API 下发 `question_id`，指定报告模板

**前置输入**（至少满足其一，否则提示补跑上游）：

| 阶段 | 最低要求 |
|------|----------|
| 基础报告 | 01 采集 + 03 核查 |
| 完整报告 | 01 + 02（可选）+ 03 + 04（可选） |
| 跨平台报告 | 02 图谱 + 各平台至少基础采集 |

---

## 三、深度模式交互流程

```
输入报告主体（账号 / 实体图谱 / question_id）
    │
    ▼
【确认点 A】报告类型？
    ├─ 简要摘要（1～2 页）
    ├─ 标准核查报告（推荐）
    ├─ 深度研判报告（含多模态附录）
    └─ 自定义模板
              │
              ▼
【确认点 B】包含哪些章节？（可勾选）
    ├─ 任务概述与对象说明
    ├─ 采集范围与方法
    ├─ 跨平台账号图谱（02）
    ├─ 账号基础画像
    ├─ 核查结论与风险等级
    ├─ 分维度核查详情
    ├─ 多模态分析摘要（04）
    ├─ 典型内容摘录（博文/评论）
    ├─ 证据清单与数据来源
    ├─ 待补证与局限性说明
    └─ 处置建议（可选）
              │
              ▼
【确认点 C】详略与受众？
    ├─ 内部技术版（含 tool_call 索引）
    ├─ 业务研判版（结论优先）
    └─ 对外简版（脱敏）
              │
              ▼
【确认点 D】输出格式？
    ├─ Markdown
    ├─ HTML
    ├─ JSON（结构化）
    └─ Markdown + JSON 双输出
              │
              ▼
    ┌─ 汇总证据包 + 生成报告草案 ─┐
    └──────────────────────────────┘
              │
              ▼
【确认点 E】用户审阅修订
    ├─ 接受发布
    ├─ 指定章节重写
    ├─ 补充某维度后重新生成
    └─ 导出并结束
```

## 四、标准报告章节结构（推荐）

### 1. 任务概述

- 任务编号、`question_id`、生成时间  
- 核查对象（平台、账号、关联实体）  
- 用户确认的采集/核查参数摘要  

### 2. 数据来源与方法

- 使用的平台与 MCP 工具  
- 采集时间范围、关键词、数量上限  
- 核查维度与判定标准（03 确认项）  

### 3. 跨平台账号图谱（若有 02）

- 种子账号与确认关联账号表  
- 匹配置信度与用户确认记录  

### 4. 账号基础画像

- 各平台资料摘要  
- 粉丝/关注、注册时间、认证状态  
- 活跃概况（发帖频率、最近活跃）  

### 5. 核查结论（核心）

| 字段 | 内容 |
|------|------|
| 综合判定 | 如：疑似虚拟营销账号 |
| 风险等级 | 高 / 中 / 低 / 信息不足 |
| 置信度 | 0～1 或文字说明 |
| 一句话摘要 | 供领导阅 |

### 6. 分维度核查详情

按 03 所选维度展开，每条含：**现象 → 证据 → 研判**

### 7. 多模态分析摘要（若有 04）

- 文本主题与立场  
- 图像/视频关键发现  
- 跨模态矛盾点  

### 8. 典型内容摘录

- 代表性博文/评论（带链接或 ID）  
- 标注「为何选取」  

### 9. 证据清单

| 证据 ID | 类型 | 来源工具 | 摘要 |
|---------|------|----------|------|
| ev_001 | profile | weibo_get_profile | … |

### 10. 局限性 & 待补证

- 未采集项、平台限制、时效说明  

### 11. 处置建议（可选）

- 持续关注、补充采集、交叉验证建议

## 五、各确认点交互文案

### 确认点 A · 报告类型

> 可为 **@某某**（含 B站关联账号 1 个）生成报告：  
> - [1] **简要摘要** — 结论 + 核心证据 3 条  
> - [2] **标准核查报告** — 完整章节，推荐  
> - [3] **深度研判报告** — 含多模态附录与内容摘录  
> - [4] 加载自定义模板 `template_xxx`  

### 确认点 C · 受众与详略

> 报告面向谁？  
> - [1] 内部技术（含证据 ID、工具名）  
> - [2] 业务研判（结论优先，附录折叠）  
> - [3] 对外简版（脱敏昵称、隐藏工具细节）  

### 确认点 E · 审阅

> 报告草案已生成（标准版，共 11 节）。  
> - [1] **确认发布**  
> - [2] 重写「核查结论」章节  
> - [3] 补充粉丝数据后全文重生成  
> - [4] 导出 Markdown + JSON

## 七、与 Hermes / 外部系统映射

| 环节 | 实现 |
|------|------|
| 章节勾选、受众确认 | `clarify` + Skill `account-verification-report` |
| 证据包汇总 | 读取 01～04 结构化产物（DB 或 session 文件） |
| 正文生成 | **draft 阶段**：模型仅基于证据包撰写，禁止调用工具 |
| 对外交付 | Gateway API / 文件输出 / Java 回调 |

---

## 八、生成原则（强制）

1. **结论必须引用证据 ID**，无证据写「暂无充分证据」  
2. **未执行的阶段不在报告中虚构**（如无 04 则省略多模态章节）  
3. **用户未勾选章节不出现在正文**  
4. **对外简版自动脱敏**（手机号、精确地址、内部 tool 名）  
5. **报告版本号**：修订后递增，保留历史草案

## 九、五类业务总览

```
                    ┌─────────────────────────────────────┐
                    │         用户下发账号 / 任务          │
                    └──────────────────┬──────────────────┘
                                       ▼
                              01 账号信息采集
                                       │
                         ┌─────────────┴─────────────┐
                         ▼                           │
                 02 跨平台账号收集                    │
                         │                           │
                         └─────────────┬─────────────┘
                                       ▼
                              03 账号核查
                                       │
                         ┌─────────────┴─────────────┐
                         ▼                           │
                 04 账号多模态分析                    │
                         │                           │
                         └─────────────┬─────────────┘
                                       ▼

```

每一环节均为 **「提示 → 用户选择 → 执行 → 再提示」** 的深度模式，可任意跳转、回退、跳过，由用户掌控节奏。
