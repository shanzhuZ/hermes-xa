# 03 · 账号核查

> **交互模式**：密塔 AI 深度模式 —— 用户提交**一批账号列表**，并明确「本人」参照信息后，系统逐账号核查，判定哪些账号**真实存在且属于本人**。  
> **定位**：从「候选账号一堆」中筛出**本人真实账号**，排除冒充、误匹配、营销小号、非本人账号。

---

## 一、业务目标

用户给定**账号列表**（可来自 02 跨平台检索、手工录入、外部系统导入），对照**本人参照信息**，批量判定每个账号的归属与真实性。

| 产出 | 说明 |
|------|------|
| 分类结果 | 本人真实 / 非本人 / 疑似冒充 / 无法判定 |
| 逐账号结论 | 是否真实存在、是否本人、置信度、主要依据 |
| 证据清单 | 每条结论可回溯到工具输出或比对记录 |
| 推荐动作 | 建议保留、排除、人工复核的账号子集 |

### 判定类别定义

| 类别 | 含义 |
|------|------|
| **本人真实** | 账号真实活跃，且证据支持为本人持有或本人运营 |
| **非本人** | 真实账号但属于他人、同名误匹配、机构号无关人等 |
| **疑似冒充** | 使用本人姓名/照片/信息，但行为或资料支持冒用、仿号 |
| **无法判定** | 数据不足、私密账号、平台不可达，不做强结论 |

---

## 二、触发条件

- 从 **02 跨平台账号收集** 携带候选列表跳转
- 用户直接提交账号清单进行核查
- 从 **05 报告** 发现结论争议，回退重核

**前置输入**：

- **账号列表**（必填）：`平台 + 账号标识`，支持批量粘贴或文件导入
- **本人参照信息**（必填至少一项）：真实姓名、已知本人账号、证件照/生活照、单位职务、手机号片段等

---

## 三、深度模式交互流程

```
用户提交账号列表 + 本人参照信息
    │
    ▼
【确认点 A】本人参照信息是否完整？
    ├─ 补充姓名、照片、已知本人主账号等
    ├─ 指定「锚定账号」（列表中哪一个确定是本人）
    └─ 确认参照信息无误
              │
              ▼
【确认点 B】核查账号范围？
    ├─ 列表全部账号
    ├─ 用户勾选子集
    └─ 排除用户已标记「确定本人」的锚定账号（仅核其余）
              │
              ▼
【确认点 C】核查侧重点（可多选）？
    ├─ 是否本人（与参照信息一致性）
    ├─ 账号是否真实存在（非注销、非伪造页面）
    ├─ 是否冒充本人（仿名、盗图、虚假认证）
    └─ 跨账号一致性（列表内多账号是否同一自然人）
              │
              ▼
【确认点 D】证据获取方式？
    ├─ 仅用列表中已有资料/链接
    ├─ 自动拉取各账号公开资料（轻量查询）
    └─ 对判定存疑账号补充采集（跳转 01，确认后执行）
              │
              ▼
    ┌─ 批量核查（规则 + 比对 + 模型归纳）─┐
    └────────────────────────────────────┘
              │
              ▼
【确认点 E】展示分类结果，用户确认或调整？
    ├─ 接受系统分类
    ├─ 手动改某账号类别
    ├─ 对「无法判定」项补充证据后重跑
    ├─ 进入 04 多模态分析（针对盗图/冒充疑点）
    ├─ 进入 05 生成核查报告
    └─ 结束
```

## 四、核查逻辑说明

### 4.1 是否本人（核心）

| 比对项 | 说明 |
|--------|------|
| 姓名/昵称 | 与本人姓名、常用网名是否一致或合理变体 |
| 头像/形象 | 与本人参照照片是否一致（可交 04 图像比对） |
| 简介/职业 | 单位、职务、地域是否与已知信息吻合 |
| 内容风格 | 发文话题、语言习惯是否符合本人 |
| 关联证据 | 是否出现本人其他已确认账号的互关、@、同框 |

### 4.2 是否真实存在

| 检查项 | 说明 |
|--------|------|
| 账号状态 | 是否存在、是否注销、是否私密不可见 |
| 资料可验证 | 粉丝、发文、认证等是否可正常获取 |
| 异常伪造 | 是否像批量生成壳号、无真实互动 |

### 4.3 是否冒充本人

| 检查项 | 说明 |
|--------|------|
| 盗用照片/姓名 | 资料像本人但行为异常、引流、诈骗话术 |
| 认证矛盾 | 认证主体与声称身份不符 |
| 与锚定账号冲突 | 同平台出现多个「都像本人」的号 |

### 4.4 列表内一致性

对批量账号做聚类：哪些应归为**同一自然人**，哪些应拆分为**不同人**，避免 02 检索带来的同名误并。

## 七、与 Hermes 的映射

| 环节 | 实现 |
|------|------|
| 列表导入、参照信息确认 | `clarify` + Skill `account-verification-batch` |
| 批量拉资料 | 各平台 MCP `get_profile` 等 |
| 头像/照片比对 | Vision MCP，疑点跳转 04 |
| 规则聚类与打分 | Python 脚本（确定性逻辑） |
| 结论归纳 | 模型仅基于证据表，禁止无据定性 |

---

## 八、原则（强制）

1. **必须有「本人」参照锚点**（锚定账号或姓名+照片等），否则只做存在性检查，不做本人判定  
2. **每条账号结论独立**，附证据 ID，可复核  
3. **无法判定时归入 `insufficient_data`**，不强行划入本人或非本人  
4. **用户可在确认点 E 覆盖系统分类**，以用户最终确认为准写入正式结果  
5. **02 候选账号默认全部为待核查项**，是否在 02 高置信 ≠ 本人真实
