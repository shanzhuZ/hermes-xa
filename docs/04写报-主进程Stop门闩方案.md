# 04 写报 · 主进程 Stop 门闩方案（草案）

> **状态**：第二期已落地——碰撞真空 + 碰撞齐后发文未落地均拦截 stop；续跑逻辑未改。  
> **范围**：防止主进程因「四、关联碰撞」（含刚齐却复述步骤4收束）而结束；**不改动现有续跑**。  
> **实证**：`b022` / `7e47`（碰撞齐后仍「步骤4完成」+ stop → 第一期放行；第二期应拦并催发文）。  
> **关联**：`scripts/report_04/stop_gate.py`、`sink.py`；Hermes `conversation_loop.py`（`pre_verify`）。

---

## 1. 问题陈述

### 1.1 现象

主进程在「三、账号采集」（执行树 `step4_profiles`）结束后，常输出「步骤4完成…」并以 **`finish_reason=stop`** 结束对话循环。  
此时系统仍在后台自动推进「四、关联碰撞」（4.1 文本/图片核验 → 4.2 validated → 4.3 社工库）。  
主进程已死，模型看不到碰撞进度，也无法同会话接着调发文工具。

### 1.2 证据（b022）

| 环节 | 事实 |
|------|------|
| 主进程末条 | assistant「步骤4完成…」，`finish_reason=stop`，无工具 |
| 碰撞 | Hook/系统在步骤 4 后静默跑完 4.1～4.3 |
| 发文 | 约数十秒后由续跑注入 user「发文已开放…」，再调 tweets / YouTube |
| 结论 | 发文靠**续跑兜底**可跑通；主进程断流是体验与可靠性的主痛点 |

### 1.3 已证伪的手段

| 手段 | 为何不够 |
|------|----------|
| 进度看板 / `pre_llm` context | 只能劝，拦不住 `stop` |
| `post_llm` 再返回 context | Hermes `turn_finalizer` **丢弃返回值**，对循环无效 |
| 指望模型自觉「每几秒查库」 | 无稳定白名单工具；且模型更常直接 stop |
| 现成 Hermes `pre_verify` | **仅当本轮有文件修改（`_edited`）才触发**，写报用不了 |

### 1.4 设计约束（本次）

1. **不改**现有续跑状态机、inflight、`osint_done` 催发文等逻辑。  
2. 目标：**主进程在碰撞未完成（及后续未到可合法结束的状态）时，禁止自动结束**。  
3. 续跑继续作为兜底（b022 已证明可行）。

---

## 2. 目标与非目标

### 2.1 目标

- 步骤 3（主页采集）收口后，主会话**不得**因纯文本「步骤4完成」而 `stop`。  
- 主进程应进入「等待碰撞 / 调等待工具 / 门禁开后立刻发文」之一，直到碰撞完成并可采发文。  
- UI 上能区分：系统在推碰撞 vs 主会话已死。

### 2.2 非目标（本次不做）

- 不重写续跑、不修 posts→analysis 链式（另案）。  
- 不把进度看板当成保活主方案。  
- 不要求模型自己轮询 MySQL（见 §5 可选工具封装）。

---

## 3. 推荐方案：主进程 Stop 门闩

### 3.1 思路

在对话循环即将因「无工具 + stop」退出时，增加写报专用判定：

**若任务为 `account_report`，且流水线尚未允许结束，则拦截 stop，注入合成 user，并 `continue` 主循环。**

这与续跑不同：

| | Stop 门闩 | 续跑 |
|--|-----------|------|
| 时机 | 主进程**还在**、正要 break 前 | 主进程**已结束**后另开 SSE |
| 实现点 | Hermes 循环 / 扩展 stop-nudge | `maybe_continue_agent_session` |
| 本次 | **要做** | **不动** |

### 3.2 触发条件（第二期）

`step4_profiles` 已终态，且尚无终稿时：

| 原因码 | 条件 | 催促 |
|--------|------|------|
| `collision` | `step5` / `step6_validated` / `step6_osint_es` 任一未终态 | 保持会话，等碰撞；禁止复述步骤4 |
| `posts` | 碰撞已齐，且发文门禁开、仍有未尝试平台或帖数为 0 | 立刻调发文工具；禁止再复述步骤4 |

发文实质已齐（`posts_substantively_ready`）或已有终稿 → **放行 stop**（分析/终稿仍可由续跑兜底）。

### 3.3 拦截后行为

1. 将本轮 assistant 文本保留在历史（可标 synthetic，避免当终稿）。  
2. 追加合成 user，例如：

```text
【系统·禁止结束会话】三、账号采集已收口，四、关联碰撞仍由系统推进中（4.1/4.2/4.3）。
禁止 stop。请调用 wait_collision（若已提供）等待碰撞完成；
完成后立刻对 validated 调用发文工具。禁止只复述「步骤4完成」。
```

3. `continue` 主循环，进入下一轮 LLM（可先 `pre_llm` 再推碰撞进度）。  
4. **限次**：单任务连续门闩次数上限（建议 5～8），防止死循环；达上限则放行 stop，交给现有续跑兜底。

### 3.4 落地路径

#### 路径 A（推荐）：Hermes 写报专用 stop-nudge

- 在 `conversation_loop` 于现有 `pre_verify`（需 `_edited`）旁增加：  
  `account_report` 且满足 §3.2 → 调 Hook / 本地函数取 nudge 文案 → 与 verify-on-stop 相同地 `continue`。  
- 或：放宽 `pre_verify` 对 `account_report`：**不要求 `_edited`**，由 `db_sink` 注册 `pre_verify` 返回 `{"action":"continue","message":"..."}`。

**配置**：`config.yaml` / `sync_collect_hooks.py` 增加 `pre_verify` → `db_sink.py`；allowlist 同步。

#### 路径 B（辅助）：`wait_collision` 工具

- 白名单工具：进程内每 2～3 秒查 `collect_phase_steps` / 阶段壳，直到碰撞终态或超时（如 180～300s）。  
- Skill / `collect-rules` 写明：步骤 3 后必须先调此工具，禁止纯文本收束。  
- **单独不够**：模型仍可无视去 stop；须与路径 A 组合。

### 3.5 涉及文件（预计）

| 文件 | 改动 |
|------|------|
| `hermes-agent/agent/conversation_loop.py` 或 `verify_hooks` 相关 | 写报 stop 门闩触发（若走 A） |
| `scripts/report_04/sink.py` | `pre_verify` / 门闩文案与条件 |
| `scripts/db_sink.py` | 透传 `pre_verify` 返回 |
| `config.yaml` + `sync_collect_hooks.py` + allowlist | 注册 `pre_verify` |
| Skill / `collect-rules.yaml` | 禁止步骤 3 后纯文本结束；可选 `wait_collision` |
| （可选）新工具模块 | `wait_collision` 实现 |

**明确不改**：`session_continue.py` 主路径、`osint_done` 催 posts 的现有行为。

## 4. 验收标准

新开写报任务，在主页采集完成后：

1. **不应**出现：仅「步骤4完成」+ 主进程立刻静默结束、长时间无任何同会话跟进。  
2. **应**出现：Stop 被拦截后的合成催促，和/或 `wait_collision` / 发文工具调用。  
3. 发文尽量发生在**同一主会话**；若门闩达上限，续跑仍能兜底（回归 b022 能力）。  
4. 有终稿后允许正常 stop，不得无限拦截。

## 6. 附录：系统自动步「改成模型可调工具」可行性评估

> 想法：主进程爱断，是因为中间有一段「系统自动跑、模型无工具可调」的真空。若把 4.1 / 4.2 / 4.3 等系统自动节点都封装成工具，写进 Skill/规则，全链路由模型自己调，是否可行？

### 6.1 结论（先说）

| 判断 | 说明 |
|------|------|
| **部分可行** | 适合「一次调用、结果明确、失败可 skip」的步骤 |
| **不建议整段 4.1～4.3 全改成模型工具** | 真空会变成「模型漏调 / 调错 / 超时 / 假完成」，比系统自动 + Stop 门闩更脆 |
| **更优组合** | **系统自动保留** + **Stop 门闩保主进程**（本文 §3）；续跑兜底不动 |

### 6.2 为何「全链路模型调工具」看起来诱人

- 每一档都有 tool_call → 不易出现「无工具可调 → 只能说话 → stop」。  
- Skill 叙事与执行一致：「步骤 X 调工具 Y」。  
- 排障时工具日志完整。

### 6.3 主要风险

1. **漏调即卡死**  
   今日系统保证 4.1→4.2→4.3 顺序推进；改成工具后，模型漏调 4.2 或跳过 4.3，门禁与步骤树会对不齐。需要大量「未调则 Hook 代跑」——又变回系统自动。

2. **长耗时不适合作同步工具**  
   4.1.2 图片管线、4.3 ES 常要数十秒～数分钟。塞进单次工具：  
   - 易撞 Hook 120s / 工具超时；  
   - 或工具只「kickoff」立刻返回 → 模型仍面临「等结果」真空，**问题平移**。

3. **确定性逻辑不该交给模型**  
   `run_validated_accounts`、社工库 URL 列表、覆盖度收口是规则引擎。让模型「调用收敛工具」可以，但**收敛算法仍应在工具内部**；若指望模型用自然语言决定 validated，质量与一致性会下降（已有「不宜启动步骤6」类胡话）。

4. **Skill/白名单膨胀**  
   每多一个必须工具，就多一轮失败重试与抢跑拦截；编排复杂度上升，不一定减少断流。

5. **与续跑关系**  
   即使全是工具，模型仍可能在中途 stop（历史已多次证明）。**没有 Stop 门闩或续跑，全工具化也不能保证主进程不断。**

### 6.4 若坚持「工具化」，建议的边界（可试点，勿一次全切）

| 步骤 | 建议 | 理由 |
|------|------|------|
| 4.1.1 文本核验 | 可保留 Agent 输出结论；**规则比对仍系统** | 已有标记解析 |
| 4.1.2 图片管线 | **保持系统后台**；或提供 `kickoff_image_pipeline`（异步）+ Stop 门闩等待 | 不宜同步堵工具 |
| 4.2 validated | 可提供 **`run_validated` 一键工具**（内部仍是现网算法） | 模型只负责「调用」，不负责判定 |
| 4.3 社工库 | 可提供 **`run_osint` 一键工具**（内部现网 ES 管线） | 同上；失败工具内 skip |
| 发文/分析 | 保持现有 MCP 工具 | 本就是模型调 |

即：**「一键系统步」工具化可以试点**（把自动跑收成显式 tool_call，消灭「无工具」错觉），**不要把管线拆成让模型逐步拼装的一堆微工具**。

即便做了「一键工具」，仍建议保留：

- 步骤 4 收口后的 **Stop 门闩**（防根本不调）；  
- 超时未调则 **系统代跑**（与今日 `_auto_step5_step6` 同级兜底）；  
- **续跑不动**。

### 6.5 与本文方案的关系

```
优先落地：Stop 门闩（§3）     ← 直接防主进程 stop
可选试点：4.2/4.3 一键工具     ← 减少「真空无工具」体感
不推荐：  取消系统自动、全靠模型逐步编排
保持：    续跑兜底（已验证）
```
