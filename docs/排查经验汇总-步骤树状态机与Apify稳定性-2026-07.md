# 排查经验汇总：步骤树状态机、流式中继与 Apify 稳定性（2026-07）

> 本文整理自 2026-07 中下旬前后多轮联调（01 采集 / 02 扩建 / 03 核查 / 04 写报）中的真实故障与修复沉淀。  
> 目标：把「会再踩」的坑写全，供后续改 Hook / Java 粗同步 / Skill / Gateway 时对照。  
> 相关旧文：`docs/账号采集-问题根因分析.md`、`docs/思考流与步骤树同步落库实施方案.md`。

---

## 0. 总原则（先记住）

1. **步骤树真相源是 Hook（Python）+ 库表事实**；Java `CoarseStepSync` 只是粗同步，不能当业务状态机。
2. **偏好中间态 `running`，慎用过早终态**（`failed` / `skipped`），否则 Agent 稍后成功会造成 **fail→running 翻烧饼**。
3. **「工具 HTTP/Actor 成功」≠「有可入库主页」**。Apify 可 `SUCCEEDED` 且 `itemCount=1` 但仍是空壳（`cleanItemCount=0`）。
4. **业务任务 `failed` ≠ Agent 已停**。不 interrupt Gateway / 不断开 SSE，模型仍会继续 `web_search`，stream 与流程图错位。
5. **按平台判定兄弟节点是否终态**，不能按单个 `step_key`（主页/发文互为 pending 会死锁）。
6. 改状态机前尽量用 **真实 task_id + `hermes_tool_outputs` + agent.log 时间线** 复盘，达到高把握再出手。

## 2. 详细案例

### 2.1 幽灵采集任务 + 假 Instagram 种子（01）

**现象**

- 扩建任务失败后，库里突然出现无关的采集任务。
- 种子被解析成 Instagram，展示名怪异（如「李老师」）。

**根因**

1. `collect_01` / `expand_02` sink 在 `mcp_*` 无法解析 task 时走 `ensure_task(...)` 兜底，**凭空建孤儿任务**。
2. 平台解析短别名 `ig` 用子串匹配，命中 `intelligence` 等词（skill 名前缀污染）。

**修复方向**

- 去掉 mcp 路径的孤儿 `ensure_task`。
- 平台解析：去掉 skill 前缀 + 短别名用词边界；Java CreateService 与 Python `seed_platforms` 对齐。

**教训**

- Hook 的「兜底建任务」比漏绑 session 更危险——会污染任务树与前端列表。
- 短别名（`ig`/`fb`/`tg`）一律严禁裸子串匹配。

---

### 2.2 扩建：父节点晚于子节点 running（02）

**现象**

- `step4_image_compare` 已 running，而逻辑父 `step3_streams` 仍 pending（或子先于父几十秒）。

**根因**

- Java 粗同步只把「工具映射到的目标 step」写成 running，未保证逻辑父先亮。

**修复方向**

- `CoarseToolStepMapping.parentsToEnsureRunning`：点亮子步骤前先粗写父节点。
- Hook 侧亦确保「先父后子」。

**教训**

- UI 顺序敏感：用户把「步骤树左右顺序」当执行真相；父晚于子会被直接当成产品 bug。

---

### 2.3 扩建：遗留 `step6_posts`（2.9）干扰（02）

**现象**

- 步骤树出现废弃发文父节点；影响 step2/step3 时序观感与竞态。

**根因**

- 历史预建逻辑仍插入 expand 的 `step6_posts`，而业务树已迁移到 `step3_profiles` 下的 `step3_post_*`。

**修复方向**

- Expand 创建任务不再插入；存量 DELETE；collect 的 `step6_posts` 可保留（若 01 仍用）。

**教训**

- 步骤树 schema 演进必须有「停插 + 存量清理」，否则旧节点会长期制造幽灵竞态。

---

### 2.4 YouTube：failed「需 channelId」→ 稍后又 running（03）

**现象**

- 步骤 2.3 YouTube 主页很快 `failed`：`YouTube 需 channelId（UC…）`。
- 发文被 skip。
- 过一段时间 Agent 查到真 UC，再调 MCP → 步骤又变 `running`/`completed`（翻烧饼）。

**根因**

1. Agent 会先传伪 UC（如 `UCwhyyoutouzhele`）或 `@handle`；工具失败。
2. 旧逻辑：**非法 channelId 直接 `failed`**。
3. 真 UC（通常 24 位，`UC`+22）后来成功 → 状态重开。

**修复方向**

- `youtube_channel_id_ok`：`UC` 开头且长度 ≥ 22。
- 非法 UC / @handle 失败：**保持 `running`**（等待重试），勿立即 failed。
- reconcile 终态失败：**仅当合法 UC 调用失败且无成功**。
- 其它平台均终态而 YouTube 仍卡「等待合法 UC」→ session/peer 收口 skip。

**教训**

- 「参数还不对」应是 **进行中**，不是失败。
- 终态文案不要写死「需要 UC」当通用失败——会误导并掩盖真失败原因。

---

### 2.5 Apify TG/FB/INS：「已拉取 dataset 但未入库主页」（03）

**现象**

- Actor / `get_dataset_items` 工具 status=success，步骤却 failed，文案像入库 bug。
- Instagram 甚至可能用「仅 username 的 not_found 壳」假入库。

**根因（实测数据形状）**

| 平台 | 典型「假成功」载荷 |
|------|-------------------|
| Telegram | `status: not_found` |
| Instagram | `error: not_found` 或仅 username 无 biography/followers 等信号 |
| Facebook | `type=profile` 但 id/url/name 全空（空壳） |

**修复方向**

- Normalizer：`_item_is_unavailable`；Instagram 要求实质字段；Facebook 拒空壳；Telegram 跳过 unavailable。
- 返回 `collect_outcome`：`ok` / `not_found` / `empty`。
- 步骤文案：`账号不存在或不可用` / `dataset 无可解析主页`，禁止笼统「未入库」。

**教训**

- **必须先 unwrap MCP 载荷再看 items**（`unwrap_tool_payload`）。
- 成功判定以 **可入库字段** 为准，不以 Actor exitCode=0 为准。

### 2.6 YouTube 一直 pending → 步骤2永远 running（03）

**样例任务**：`fff4bfb2-fad9-434a-8e72-a445ef655d84`

**现象**

- Twitter/FB/INS/TG 已终态；YouTube 主页+发文一直 `pending`。
- `step3_profiles` 卡 running；Agent 已跳去 `vision_analyze`。

**根因叠加**

1. 为防「Apify 速失败误 skip YouTube」，曾把 `aggressive=False` 的 auto_skip **整段关掉** → 弃采 YouTube 时无人收口 → **过猛**。
2. 旧 peer 判断：`_all_other_children_terminal(skip_step_key)` 按**单 step**排除；YouTube **主页与发文互相等待** → **死锁**，永远 skip 不掉。
3. Agent 日志显示：**从未调用任何 youtube MCP**，直接 vision。

**修复方向**

- 恢复中途 peer-skip，但改为 **`_all_other_platforms_terminal(platform)`**（忽略本平台主页+发文互锁）。
- 先收口主页再发文；发文在主页已 failed/skipped 时可直接 skip。
- 后续 MCP 仍可从 skipped reopen → running。

**教训**

- 防误杀时不要用「完全关闭收口」这种一刀切。
- 任意「兄弟终态」算法必须按 **平台维度**，并注意同平台双子节点。

---

### 2.7 步骤3 进行中步骤4 被点亮（03）

**样例**：同上 `fff4bfb2`，也见于多次 vision 抢跑。

**现象**

- `step3_streams` message=`子步骤执行中`
- `step4_image_compare` message=`执行 vision_analyze`
- 而 `step3_profiles` 仍未完成

**根因**

- `CoarseToolStepMapping.resolveVerify`：Vision/OCR → `step4_image_compare`
- `parentsToEnsureRunning`：点 step4 时先粗写 `step3_streams`
- Agent 违反 Skill「vision 仅后期」仍提前调 vision → **UI 显示步骤跳跃**

**修复方向**

- `CoarseStepSync.isVerifyStep4Blocked`：
  - verify：`step3_profiles` 与 `step3_streams` 均需 `completed` 才允许粗点亮 `step4_*`
  - collect/expand：至少 `step3_profiles` completed
- Hook 侧本就有 `can_advance_to_step45`；Java 粗同步必须对齐门禁。

**教训**

- Skill 禁令挡不住模型；**UI 门禁必须写在粗同步 / Hook 双端**。
- 「父节点占位 running」也会造成用户以为步骤3已开始，慎用。

### 2.8 04 写报：Facebook Apify 种子失败（laowhy86）

**样例任务**：`ce942d2a-9e35-4b4c-b4b6-9445206777f8`  
**用户输入**：深度画像 facebook 用户：laowhy86

**现象**

- 历史上同账号多次 collect/report 成功。
- 本次 Actor + dataset 工具均 success，但步骤1 failed：种子主页无结果；后续步骤全部 skipped。

**库内事实**

- Actor：`SUCCEEDED`，`runTimeSecs≈5.5`，`itemCount=1`，**`cleanItemCount=0`**
- Dataset item：空壳 profile（name/id/url/followers 全空）
- 历史成功项：`id=100040158655292`，`followers=14K`，`profile_intro_text=Matthew Tye from Laowhy86!`

**本地实测（同 Token、同 Actor、同 URL，失败后不久连测 3 次）**

| 次数 | waitSecs | 结果 |
|------|----------|------|
| 1 | 45 | 成功完整 profile |
| 2 | 30 | 成功 |
| 3 | 45 | 成功 |

**结论**

- **不是账号不存在**，是 **Apify Facebook Actor 偶发空壳**。
- Hook 判空失败是对的；缺的是 **空结果自动重试 1 次**（尚未完全产品化时，至少要在经验上有意识）。

**教训**

- 排障顺序：先拉 dataset 原文 / `cleanItemCount`，再怀疑账号；能的话 **当场复测 Apify**。
- 文案应区分「账号不存在」与「Apify 空结果，可重试」。

### 2.9 任务已 failed，stream 仍输出 web_search（04，通用）

**样例**：`ce942d2a`，session `api_1784133702_9c7b3d0d`

**时间线**

| 时间 | 事件 |
|------|------|
| 00:42:45 | Hook `fail_seed_and_abort`，任务 failed，步骤 skip |
| 00:43:16+ | agent.log 仍出现多轮 `web_search` / firecrawl |
| 库内 | 该 task 的 `hermes_tool_outputs` 往往只有 Apify 两行（步骤树不再推进，但 **SSE/思考流仍推事件**） |

**根因**

1. `fail_seed_and_abort` 只改 MySQL，**不打断 Hermes Agent**。
2. `/api/sessions/{id}/chat/stream` 旧实现对客户端断开主要 `task.cancel()`，**未 `agent.interrupt()`**；executor 线程里 `run_conversation` 继续跑。
3. ThoughtStreamHub 仍转发后续 tool/assistant 事件 → **流程图与 stream 严重不一致**。

**修复方向**

- Gateway：session SSE 断开时 `agent.interrupt(...)`。
- Java `HermesGatewayClient.drainStream`：检测到 `hermes_tasks.status=failed` → disconnect SSE + 发 `run.failed`。
- `ThoughtStreamHub`：任务已 failed 时丢弃后续非终态 Gateway 事件。

**教训**

- 「终止任务」= **库终态 + Agent interrupt + 中继停发** 三件套。
- 查错别只看 `collect_phase_steps`，一定对照 **agent.log**。

## 3. 易混概念对照

| 概念 | 含义 | 常见误判 |
|------|------|----------|
| Actor `SUCCEEDED` | 进程退出码成功 | 当成「有用户数据」 |
| `itemCount=1` | 有一条 item | 当成有效主页 |
| `cleanItemCount=0` | 清洗后无有效项 | 忽略此字段会误判 |
| 工具 status=success（Hook） | MCP 调用未抛错 | 当成业务成功 |
| `collect_outcome=not_found` | 明确不可用 | 写成「未入库」像 bug |
| step skipped | 业务放弃该支路 | 当成系统错误 |
| Java 粗 running | UI 提示正在执行 | 当成步骤已合法推进 |
| 任务 failed | 业务终态 | 当成会话/Agent 已停 |

## 4. 状态机设计备忘（03/04）

### 4.1 YouTube

```
非法 UC / @handle 失败 → running（等待合法 UC）
合法 UC 失败且无成功 → failed（可 session 收口）
其它平台均终态 + 仍无结果 → skip/fail 解开父步骤
后续真 MCP 成功 → 允许 skipped/failed reopen → completed
```

### 4.2 Apify 平台

```
Actor 成功、dataset 未拉 → running（等待 dataset）
dataset 成功 + outcome=not_found/empty → failed（准确文案）
dataset 成功 + 有 profile/posts → completed
主页轮 0 posts → 勿 skip 发文（留给发文轮/收口）
```

### 4.3 Peer-skip（中途）

```
aggressive=False：仅当「其它平台」均终态，才 skip「本平台从未开跑」的节点
按平台判断，排除本平台 profile+post 互锁
禁止：仅因 web_search 提到域名就 skip（YouTube 查 UC 误伤史）
aggressive=True：仅会话结束硬收口
```

### 4.4 步骤推进门禁

```
step3_streams（风格）不得抢在 step3_profiles 完成前 completed
step4_*（文本/图片比对）不得在 step3_streams 完成前被粗同步点亮
Vision 工具可提前回写图片流数据，但不得提前点亮 step4 节点
```

## 5. 推荐排障清单（复制即用）

对可疑 `task_id`：

1. `hermes_tasks`：status / error_message / seed_json / task_type  
2. `collect_phase_steps`：全量 step_key / status / message  
3. `hermes_tool_outputs`：按 id 时间线；重点 tool_args + 是否真调过目标平台  
4. Apify：Actor 原始输出里的 `cleanItemCount`；dataset items 字段是否空壳  
5. `logs/agent.log`：同 session 在任务 failed 之后是否仍有工具  
6. `logs/*_sink.log`：Hook 是否已 `fail_seed_and_abort` / `种子采集失败`  
7. 若怀疑 Apify：用同 Token **现测 1～2 次** Actor（区分偶发空壳 vs 账号消失）

## 8.1 Facebook 种子写报错序（2026-07-16，`70f0671e-…`）

| 现象 | 根因 |
|------|------|
| 步骤5父已 completed「兜底跳过 N 条」，stream 尚无 vision；步骤7 running 后才出 vision tools | 步骤四 peer-skip 误跳 Instagram → 父四提前 completed → kickoff 步骤5 → 90s fail-forward；此时 Agent 仍在采 Ins，vision 晚到 |
| 步骤4：工具已调，子节点仍 pending，一会直接 completed 无 running | 粗同步把 `get_user_info`/`get_channel_stats` 恒映射 `step1_seed`（已 completed 则粗同步无效）；Java 粗 running 也不接受 `skipped→running` |
| 步骤4未完时 7.2 Facebook 发文已 skipped「已纳入可信账号，但未采集到发文」 | 种子 FB 步骤1 Apify 只入 profile；步骤7未再采发文；finalize/`_reconcile_report_post_child_steps` 对 validated+0帖立即 skip；种子平台约束不足 |

**修复要点**：

## 9. 一句话经验

> **库表终态、Agent 生命周期、SSE 中继三条线必须一起设计**；  
> **Apify/MCP 的「调用成功」永远不够，要以可入库字段与复测为准**；  
> **步骤树宁肯多停在 running，也不要过早 failed/skipped 再翻烧饼。**
