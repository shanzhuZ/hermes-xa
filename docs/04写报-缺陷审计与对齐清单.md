## 1. 审计结论（一句话）

不是「模型慢」 alone，而是**步骤状态机多路径互相打架**：合法 `skipped` 被改回 `pending`、dataset 成功却未入库不收口、父壳/门禁被 ensure 回滚。树抖、任务拖死、前端看到跳过又 pending，都落在同一类问题上。

## 2. 本次任务踩中的根因（对照现象）

### 2.1 「候选」是谁定义的？

| 说法 | 对不对 |
|------|--------|
| 模型自己想的「还有候选」 | **不对** |
| 代码写入 `cross_platform_candidates` 的线索行 | **对** |

候选来源（代码路径）：

1. **Maigret 工具返回** → Hook 归一化 → `task_store.save_candidate_rows`
2. **网页检索 / extract / 模型汇总正文** → `candidate_parser` 正则抠 URL/账号 → 同样入库

「有没有候选平台」看的是该表 + `relevant_profile_platforms`，**不是**模型思考状态。

### 2.2 已经调过工具，为什么还算候选、又变 pending？

两套概念被混在一起：

| 概念 | 含义 |
|------|------|
| **候选** | 线索阶段发现「这平台可能有号」，表里还有行 |
| **主页是否采成** | 有没有进主页表、步骤是完成还是跳过 |

`materialize_step4_from_candidates` 恢复 pending 时**只看「候选表还有该平台」**，**不看**是否已调过 YouTube/Facebook 工具。

典型时间线：

1. `tool.started`（甚至失败/超时）→ 安静期超时 → 标「超时未采集，已跳过」
2. 候选表里 facebook/youtube 行还在
3. 再次物化步骤四 → 「有候选、可采」→ **又改回 pending**（文案常为「xxx 待主页采集」）
4. Agent 再起一轮 scraper / `get_channel_stats`

该任务实测曾出现：**候选十几条，主页表仅种子 Twitter 一条**。

### 2.3 是不是最近改 `source_tag` 导致的？

**不是。**  
「有候选就把 skipped 改回 pending」逻辑在 `task_store.py` 中自 **2026-07-15** 起存在；近期改动只给 INSERT 加了 `source_tag` 字段，未改这段恢复逻辑。

## 5. 缺陷清单（按严重度）

### 5.1 P0（必须先修，否则树抖、任务拖死）

#### P0-1 materialize 无差别把 skipped 打回 pending

- **现象**：超时 skip /「dataset 已拉但未入库」后，再 materialize 又变 pending，Agent 反复重采。
- **根因**：`task_store.py` → `materialize_step4_from_candidates`：`plat in relevant_set and cur == "skipped"` 即改 pending，不区分误 skip / 合法终态。
- **违反**：跳过应终态；禁止反复回 pending。
- **建议**：仅白名单「误 skip」文案可回开；「超时未采集 / dataset 未入库 / 无线索」保持终态并禁同平台再采。

#### P0-2 abandoned 超时收口与 materialize / ensure 打架

- **现象**：`maybe_close_abandoned_step4` 超时 skip 并关父壳、甚至已推 step5 后，materialize 又把子步 pending → `ensure_step4_parent_not_premature` 回开父壳并把后续阶段打回 pending。
- **根因**：`step_reconcile.py` abandoned / force_skip 与 `materialize_step4_from_candidates`、`ensure_step4_parent_not_premature` 无协同；热路径连环触发。
- **违反**：超时终态不稳、父壳无法收口、硬门禁被回滚。
- **建议**：超时/会话 skip 打不可回开标记；ensure 忽略此类假「晚到 pending」。

#### P0-3 Apify/Telegram：dataset 成功但业务表空 → 不终态或被回开

- **现象**：主页侧 skipped「已拉取 dataset 但未入库主页」后被回 pending；发文侧 raw_items>0 却长期 running「待补字段」，父壳关不上。
- **根因**：`reconcile_step4_and_step7_children`、`sink._sync_platform_collect_steps` 完成判定偏「工具 success」，未强制「入库或终态 skip」。
- **违反**：以入库为准。
- **建议**：dataset success 且 profiles/posts 仍为 0 → 有限次 replay 后 **skipped/failed 终态**，pre_tool 禁同平台再采。

#### P0-4 `set_step_status` 对终态→pending 几乎无门闩

- **现象**：任意调用方可把 completed/skipped/failed 改回 pending（清空时间戳）。
- **根因**：`task_store.set_step_status`：`force_reopen` 只管部分父壳场景，`pending` 分支无终态保护。
- **违反**：所有「回 pending」漏洞的公共放大器。
- **建议**：终态→pending/running 默认拒绝；仅白名单原因 + `force_reopen` + 日志。

#### P0-5 step7「Actor 已跑未拉齐」skip 与「空 skip 回开」互刷

- **现象**：一边标 skipped，一边每轮 reopen 成 pending；父壳因 leftover 关不掉。
- **根因**：`_maybe_skip_step7_actor_stale` vs `reopen_unattempted_empty_skipped_posts`（`engine.run_post_tool_light` 热路径）。
- **违反**：状态抖动，而非稳定逼拉 dataset 或稳定终态。
- **建议**：actor_without_dataset 保持 running + 硬拦；超时后一次 skipped，且不再 reopen。

---

### 5.2 P1（门禁 / 补采 / 父壳时序）

#### P1-6 发文父壳完成后仍允许 late 补采

- **现象**：子步 skipped、父 completed 后仍可发文/Apify；入库后 force_reopen 把 skipped→completed。
- **根因**：`orchestrator._allow_late_step7_post_collect`；sync/reconcile 的 `force_reopen`；`start_step7_if_ready` 可 reopen 父壳。
- **违反**：与《步骤7跳过禁止补采》策略 A 相反。
- **建议**：删除或开关化 late-collect；skipped 平台 pre_tool 硬拦。

#### P1-7 ensure_* 把终态降回 pending

- **现象**：纠正抢跑时，step5/6/7/osint 等从 skipped/completed 被打回 pending。
- **根因**：`ensure_step5/6_not_premature`、`ensure_osint_not_premature`、`ensure_step7_parent_not_premature` 等。
- **违反**：终态不稳；与 abandoned/materialize 叠加连环回滚。
- **建议**：纠正只针对误标 running；已终态除非「违规空过」否则不降级。

#### P1-8 步骤4白名单过宽 / dataset 拦截边界糊

- **现象**：步骤4期间可跑发文向 Apify；dataset 特判导致 phase 误标时漏拦。
- **根因**：`orchestrator._STEP_WHITELIST["step4_profiles"]`；`sink._is_premature_step7_tool`。
- **违反**：抢跑可拦不完整 → 工具 success、业务表空、步骤态乱。
- **建议**：步骤4仅主页语义 Actor + 对应 phase 的 dataset；步骤7 dataset 必须过发文门禁。

#### P1-9 父壳 / phase_* 时序多路径争用

- **现象**：「壳已完成、子仍 pending」或 pending↔running↔completed 反复闪。
- **根因**：`_ensure_phase_shell_running` / `_maybe_complete_phase_shell` 与 `ensure_step7_awaits_agent_tool` 等争用。
- **建议**：壳状态只由「子步聚合 + 明确 kickoff」驱动；收口后禁 reopen（策略 A）。

#### P1-10 「禁止空 skip」与「会话结束一律 skip」语义打架

- **现象**：同一 skipped 既当「违规空过可回开」又当「会话终态」，随后 reopen 再抖。
- **建议**：skip 分类（empty_skip / timeout / no_data / session_end）；reopen 只认 empty_skip。

---

### 5.3 P2（放大问题）

#### P2-11 热路径 reconcile / materialize / ensure 过频

- **现象**：每个 post_tool、每轮 pre_llm 狂跑 abandoned + ensure + reopen + materialize。
- **影响**：放大 P0 振荡，Hook 易超时。
- **建议**：候选集变化才 materialize；ensure/reopen 状态哈希未变则跳过。

#### P2-12 超时安静钟口径不稳

- **现象**：看「最近工具」而非「最近成功主页入库」，导致永不 skip 或过早 skip。
- **建议**：安静钟改为距上次成功 profile 入库/成功主页工具。

#### P2-13 抢跑双轨（sink + orchestrator）

- **现象**：一侧异常被吞掉时漏拦。
- **建议**：统一 `pre_tool_allowed` 为唯一决策。

## 7. 建议修复顺序

> 原则：**先收状态写入口与 skip 分类，再删补采，最后降频**。不要先大拆文件。

1. **`set_step_status`：终态→pending 默认拒绝**（P0-4）
2. **materialize：禁止回开超时/未入库类 skipped**（P0-1）
3. **dataset 成功且业务表仍 0：一次终态 + 禁再采**（P0-3）
4. **拆开 abandoned / ensure 回滚链**（P0-2、P1-7）
5. **关掉 late step7 补采**（P1-6，对齐策略 A）
6. **热路径降频 reconcile**（P2-11）

代码「又臭又长」的根因：同一终态被多条路径改来改去、`skipped` 没有分类。先收敛写入口，比再堆 reconcile 更有效。
