# 04 写报 · 流程图八大阶段说明（建议稿）

> **状态**：产品/信息架构草案，**尚未改代码落地**。  
> **关联**：现网执行树见 `scripts/report_04/phases.py`（11 根步 + `step4_profile_*` / `step7_post_*`）；Skill 见 `skills/account-intelligence/account-intelligence-report/`。  
> **可视化总图**：Cursor Canvas `report-04-flow-tree`。  
> **实现原则**：**展示树可以深，执行门禁必须浅**——避免「新节点无人收口」导致流程卡死。

## 0. 怎么读本文

### 0.1 两套树

| 树 | 给谁看 | 作用 |
|----|--------|------|
| **展示树** | 甲方 / 前端流程图 | 人话阶段 + 深层级，回答「模型在干什么」 |
| **执行树** | Agent / Hook / 门禁 | 基本仍认现有 `step1`～`step11`（+ 平台子步）；新增 gate 尽量 ≤1～2 |

### 0.2 节点分级（防卡死）

| 级别 | 含义 | 是否挡住下一阶段 |
|------|------|------------------|
| **C · 真门禁** | 状态参与编排；未终态则拦工具 / 不进下一阶段 | **是** |
| **B · 系统自动** | 入库或 Hook 自动写 completed/skipped，不靠 Agent | 否（或仅弱提示） |
| **A · 纯展示** | 由 C/B 状态投影；可不进 `collect_phase_steps` | 否 |

**约定**：父节点收口时，子叶 `completed` / `skipped` / `failed` **都算终态**；无数据的枝 **不建空节点**。

### 0.3 建议目标结构（L1）

```
一、锁定目标 → 二、线索发现 → 三、账号采集 → 四、关联碰撞
 → 五、内容采集 → 六、资产沉淀 → 七、深度研判 → 八、报告生成
```

## 一、锁定目标

**甲方一句话**：先确认要查谁，并采下种子账号主页。

### 要做的事

1. **解析任务意图**（平台 + handle / channelId / uid）。
2. **采集种子主页**（只 profile，不采发文）。
   - MCP 平台：Twitter / 微博 / YouTube / B 站。
   - Apify 平台：Instagram / TikTok / Telegram / Facebook / GitHub（Actor → run → dataset，只取主页）。
3. 登记头像、外链等后续碰撞所需字段。

### 建议子树

| 展示节点 | 级别 | 现网映射 |
|----------|------|----------|
| 一、锁定目标 | A（聚合） | `step1_seed` |
| 1.1 解析任务意图 | A 或 B | 可从 `seed_json` 投影，不必新 gate |
| 1.2 采集种子主页 | **C** | `step1_seed` |
| 平台 · @种子 → 拉取 / 登记 | A | 工具输出投影 |

### 产出

- 种子 profile 入库（`collect_profiles`）。
- 种子头像等进入身份流登记（供阶段四碰撞）。

### 禁止

- 发文工具、Maigret、OCR/Vision、web_search（与现 Skill 步骤 1 一致）。

### 阶段完成条件（门禁）

- `step1_seed` ∈ {completed, skipped}（正常应为 completed）。

## 二、线索发现

**甲方一句话**：全网找「可能是同一个人」的社交账号线索。

### 要做的事

1. **全网同名探测（Maigret）**  
   - 仅允许 `mcp_maigret_collect_accounts(username=种子handle)`。  
   - 读 `summary.accounts`，形成候选草稿。
2. **网页检索补全**  
   - 仅本阶段允许 `web_search` / `web_extract` / `browser_*`。  
   - 严查 X / Facebook / Telegram / YouTube / GitHub / Reddit / 微博 / LinkedIn / Instagram / VK 等。  
   - YouTube 候选必须落到正式 `UC…` channelId（禁止把 `@handle` 当 channelId）。
3. **候选合并去重**  
   - Maigret + 网页结果按「平台 + handle」去重，形成**统一候选列表**供阶段三遍历。

### 建议子树

| 展示节点 | 级别 | 现网映射 |
|----------|------|----------|
| 二、线索发现 | A（聚合） | `step2_maigret` + `step3_web_search` |
| 2.1 全网同名探测 | **C** | `step2_maigret` |
| 2.1.x 发现候选清单 | A/B | 候选行投影 |
| 2.2 网页检索补全 | **C** | `step3_web_search` |
| 2.2.a 搜索引擎 / 2.2.b 解析 ID | A | 工具过程投影 |
| 2.3 候选合并去重 | **B** | **建议新建展示步**；由 Hook/落库后自动 completed，**不设独立 gate** |

### 产出

- 统一候选列表（平台 + handle + 可选 URL / channelId）。
- 写入跨平台候选相关表（现有候选入库路径）。

### 禁止

- 步骤 2 内使用 web_search；步骤 2 使用其它 Maigret 工具（`search_username` 等）。
- 把 Maigret 返回当画像报告输出。

### 阶段完成条件（门禁）

- `step2_maigret` 终态 **且** `step3_web_search` 终态。  
- 展示上的「二」= 二者聚合；**不要**再为 2.3 增加「必须 completed 才能进三」的硬门禁（2.3 用 B 自动亮）。

## 三、账号采集

**甲方一句话**：把候选账号的主页资料采全（能采则采，不能则跳过并说明）。

### 要做的事

1. 遍历统一候选列表（种子平台主页已在阶段一采过的，按现规则处理，避免无意义重复）。
2. **有 MCP** → 只调 profile 类工具（禁止发文工具）。  
   - YouTube：仅 `get_channel_stats(channelId=UC…)`；仅有 `@handle` 时允许例外 web 解析 UC，解析不到则 **skip**。
3. **无 MCP** → Apify 三轮，只取 profile 字段。
4. **discovery_only / 不可采平台** → 只记 URL，子步 skipped + 原因。
5. **覆盖汇总**：成功 / 失败 / 跳过 / 不可采各多少（给人看，系统写）。

### 建议子树

| 展示节点 | 级别 | 现网映射 |
|----------|------|----------|
| 三、账号采集 | A（聚合） | `step4_profiles` |
| 3.1 候选主页采集 | **C** | `step4_profiles`（父） |
| 3.1.x 平台 → 账号 · 主页 | **C** | `step4_profile_{platform}` |
| 入库 / 跳过原因 | A | message / payload 投影 |
| 3.2 采集覆盖汇总 | **B** | 系统根据子步统计自动写，**非 gate** |

### 产出

- 各候选 `collect_profiles`。
- 为阶段四准备头像 URL / 文本特征字段。

### 禁止

- 发文工具（`get_user_tweets` / `analyze_channel_videos` / `get_user_feeds` 等）。
- 全部 `step4_profile_*` 未终态前进入 Vision/OCR（阶段四）。
- 因「其它平台已采完」提前跳过尚未处理的平台。

### 阶段完成条件（门禁）

- 父 `step4_profiles` 可收口，当且仅当全部已创建的 `step4_profile_*` 均为终态（含 skipped/failed）。
- **全部主页子节点终态前禁止 vision/OCR 与发文。**

## 四、关联碰撞

**甲方一句话**：用文本和头像把「像不像同一个人」算清楚，并认定纳入/排除名单。

### 要做的事

1. **文本特征碰撞**  
   - 昵称 / handle / 简介 / 互链 / 邮箱等与种子比对。
2. **头像视觉碰撞**  
   - 仅使用库内已登记头像 URL；批次内并行 Vision；OCR 可选（无人脸文字默认可跳过）。  
   - 全部图片流终态后才收口本阶段中的核查部分。
3. **碰撞结果汇总**（分值 / 证据列表）——系统汇总，给人看。
4. **相似账号认定**  
   - `validated_accounts` = 种子 + high/medium 相似候选；其余 excluded + 原因。

### 建议子树

| 展示节点 | 级别 | 现网映射 |
|----------|------|----------|
| 四、关联碰撞 | A（聚合） | `step5_streams` + `step6_validated` |
| 4.1 文本特征碰撞 | A/B | 现并在 `step5_streams`；可展示拆叶，**不必拆第二个 gate** |
| 4.2 头像视觉碰撞 | **C**（与 5 同门） | `step5_streams`（Vision 批次） |
| 单条 OCR / Vision | A | 工具调用投影，不单独挡流程 |
| 4.3 碰撞结果汇总 | **B** | 新建展示；自动 completed |
| 4.4 相似账号认定 | **C** | `step6_validated` |
| 纳入 / 排除名单 | A/B | `validated` / `excluded` 投影 |

### 产出

- 文本流 / 图片流比对结果。
- `collect_validated_accounts`（及排除说明）。

### 禁止

- 步骤 5 未齐时调用任何发文工具。  
- 步骤 6 完成前调用发文工具。  
- 步骤 5 收口后再补 Vision。

### 阶段完成条件（门禁）

- `step5_streams` 终态 **且** `step6_validated` 终态。  
- 硬顺序：**五（内容采集）不得在 step6 完成前开始。**

## 五、内容采集

**甲方一句话**：对已认定账号拉取近期发文，作为后面分析和写报的原文证据。

### 要做的事

1. **种子账号发文**（配额偏大，供身份/习惯分析）：  
   - Twitter / YouTube / 微博走 MCP 发文工具；Apify 平台再跑一轮 dataset **入 posts**（步骤 1 的 dataset 不算本阶段发文）。
2. **关联账号发文**（validated 列表中的非种子，按平台配额）。  
   - 范围：现 Skill 约定近期发文（如约 90 天 / 条数上限，以 Skill 为准）。
3. **发文覆盖汇总**：各平台已采条数 / skipped 原因。

### 建议子树

| 展示节点 | 级别 | 现网映射 |
|----------|------|----------|
| 五、内容采集 | A（聚合） | `step7_posts` |
| 5.1 种子账号发文 | A（分组展示） | 仍落在 `step7_post_{platform}` |
| 5.2 关联账号发文 | A（分组展示） | 同上 |
| 平台 · 账号 · 条数 | **C** | `step7_post_{platform}` |
| 5.3 发文覆盖汇总 | **B** | 系统统计自动写 |

### 产出

- `collect_posts` 按平台入库。  
- 为阶段六图片发现、阶段七文本分析提供原文。

### 禁止

- web_search / browser（除历史已澄清的极窄例外外）。  
- 父 `step7_posts` 已 completed 且某平台子步已 **skipped** 后，禁止再对该平台补采（见 `docs/04写报-步骤7跳过禁止补采与Stream编排-P1P2待办.md`）。

### 阶段完成条件（门禁）

- 全部已创建的 `step7_post_*` 终态后，父 `step7_posts` 收口。  
- **收口后进入阶段六（资产），禁止直接跳进阶段七研判/阶段八写报。**

## 六、资产沉淀

**甲方一句话**：把头像、封面、发文配图（及可选视频）落库并做基础识别，方便后面「看图说话」。

### 要做的事

1. **图片资产**  
   - 发现：头像 / 封面 / 发文配图。  
   - 下载入库（HBase / `collect_images`）。  
   - OCR / Vision 回填分析字段。  
   - 命令（现网）：`python -m image_pipeline.run --task-id <taskId> --force-analyze`。
2. **视频资产（可选，后置）**  
   - 可对齐 01：选最新可下载视频 → 抽帧 → 分析；失败不挡报告。
3. **资产清单就绪**  
   - 系统标记：本阶段尝试完毕（成功条数 / 失败只记日志）。

### 建议子树

| 展示节点 | 级别 | 现网映射 |
|----------|------|----------|
| 六、资产沉淀 | A 或 **C（推荐）** | 现 Skill「7.5」**无树节点**；**建议新增 1 个 gate**，例如 `step_assets` / `step7_5_image_assets` |
| 6.1 图片资产（发现/入库/回填） | A | 管线内部阶段投影 |
| 6.2 视频资产 | A/C 可选 | 后置；默认可不建 |
| 6.3 资产清单就绪 | **B** | 管线结束自动写 |

### 产出

- `collect_images`（及分析回填字段）。  
- 可选：`collect_videos` / 帧分析。

### 禁止

- 因图片管线失败把**整任务**判 failed。  
- 跳过本阶段直接写步骤 8～11 / 终稿。  
- 终稿正文出现管线元叙述（task_id、image_pipeline、Hook 等）。

### 阶段完成条件（门禁）

- **推荐**：新增单一 gate，状态 ∈ {completed, skipped}（skipped=明确无可处理图片或管线降级完成）。  
- **过渡期**：仍可用「命令成功摘要 + Hook 兜底」投影展示「六」，但产品上应尽快进树，避免甲方看不到。

### 与编号冲突说明

- 现网平台子节点 `step_node=7.5` 表示 **Telegram 发文**，**不是**图片资产。  
- 资产进树后请使用独立 `step_key` / 展示名「六、资产沉淀」，禁止再叫「步骤 7.5」与 Telegram 混淆。

## 七、深度研判

**甲方一句话**：基于已入库的图文发文，归纳图片含义、观点涉华、身份与圈层。

### 要做的事

1. **图片语义分析**（现 step8）  
   - 头像、背景、发文配图；优先读已入库 `collect_images`，禁止对未入库临时 CDN 空跑全量。
2. **观点与涉华**（现 step9）  
   - 归纳若干核心观点；每观点 ≥3 条发文佐证（平台 + 时间 + 原文）。
3. **身份点位与圈层**（现 step10）  
   - 姓名/年龄/籍贯/常住地/活动城市/习惯/教育/工作/对华态度/电话邮箱，以及社交/亲友/同事圈层；无佐证标「证据不足」，禁止臆测。

### 建议子树

| 展示节点 | 级别 | 现网映射 |
|----------|------|----------|
| 七、深度研判 | A（聚合） | `step8` + `step9` + `step10` |
| 7.1 图片语义分析 | **C** | `step8_img_analysis` |
| 7.2 观点与涉华 | **C** | `step9_context_views` |
| 观点 → 佐证发文 | A | 分析正文/展示记录投影 |
| 7.3 身份点位与圈层 | **C** | `step10_context_pii` |

### 产出

- 三块分析展示内容（可写入 `collect_display_records` / 步骤 payload）。  
- 为阶段八四章报告提供素材（尤其是观点佐证与关联依据）。

### 禁止

- 阶段六未完成（或未降级 skipped）前抢跑 8/9/10。  
- web_search / browser。  
- 无出处的主观归纳。

### 阶段完成条件（门禁）

- `step8`、`step9`、`step10` **均可并行**；阶段「七」聚合 = 三者皆终态（未单独输出的可 skipped「终稿已出未单独输出」——与现网行为对齐）。  
- **不要**做成必须 7.1→7.2→7.3 串行，否则拉长耗时且易半截卡住。

## 八、报告生成

**甲方一句话**：汇总证据，一次输出四章画像报告。

### 要做的事

1. **汇总证据包**（profiles / posts / 碰撞结论 / 分析结果）——系统侧可自动，展示用。
2. **撰写四章正文**（必须按结构，整段叙述）：  
   - 一、账号基本信息（含 profile 与发文特征）  
   - 二、账号全网关联账号（强关联 + 文本/图片流依据）  
   - 三、账号网络活动情况（观点 + 发文作证）  
   - 四、核查思路  
3. **成稿校验**：必须以「一、账号基本信息」开头；禁止前置进度句、管线摘要、元叙述。

### 建议子树

| 展示节点 | 级别 | 现网映射 |
|----------|------|----------|
| 八、报告生成 | A（聚合） | `step11_report` |
| 8.1 汇总证据包 | A/B | 展示；非独立 gate |
| 8.2 撰写四章正文 | **C** | `step11_report` |
| 8.2.a～d 四章 | A | 终稿章节投影（可选） |
| 8.3 成稿校验 | B | 解析器/校验通过后自动 |

### 产出

- 任务终稿（summary / final-answer）。  
- 任务 phase → done。

### 禁止

- 「如果你想进一步了解…」、报告完毕套话、管线/task_id 等元叙述。  
- 无原文依据的主题归纳充数。

### 阶段完成条件（门禁）

- `step11_report` = completed，且终稿通过结构校验。

| 八 | `step11_report` |

## 附录 D · 与 Stream 流联动（甲方「规划中 → 挂出八大节点」）

### D.1 需求还原

甲方期望的体验大致是：

1. 思考流（SSE）里出现类似：**「任务规划中…」**  
2. 随后：**「已规划好：一锁定目标 / 二线索发现 / … / 八报告生成」**  
3. **流程图区域**随之展示这 **8 个大节点**（再随执行点亮子树）

结论：**能做，且推荐做「固定八阶段 + 规划开场秀」**，不要做成 05 那种「模型每次 invent 不同节点」。

> 04 的八大阶段是产品契约，不是每次临时想出来的。Stream 负责「让用户看见规划过程」，树负责「结构化进度」。二者用**结构化事件**对齐，而不是只靠模型自然语言。

### D.2 和现网能力的关系

| 现成能力 | 用途 |
|----------|------|
| `GET /api/tasks/{id}/thoughts/stream` | 思考流文案（「规划中…」） |
| `GET /api/tasks/{id}/tree` | 流程图节点与状态 |
| 05 的 `step_plan` + flow upsert | **可借鉴交互**；04 不必动态发明步骤 |
| 04 启动预插 11 步（`ReportTaskCreateService`） | 执行树已有；L1 八壳可改为「规划完成后展开/插入」 |

### D.3 推荐方案（稳、好做、不易卡死）

**原则**：规划文案可以「像 AI 在想」；**八大节点列表由系统写死下发**，Agent 只负责朗读/确认，不负责 invent。

```
用户下任务
    │
    ▼
① Java 建任务：先插「制定执行计划」节点（step_plan / phase_plan）= running
   执行用的 step1～step11 可先不暴露给前端，或 status=pending 且 UI 折叠
    │
    ▼
② Stream 推送（系统或首包）：
   - 文案：任务规划中…
   - 可选结构化事件：plan.started
    │
    ▼
③ 系统确认八阶段模板（固定列表，≤1s）
   - 文案：已规划好节点：一…八…
   - 结构化事件：plan.ready + phases[8]
   - DB：插入/展示 L1 八大父节点（pending）
   - step_plan → completed
    │
    ▼
④ 前端收到 plan.ready 或下次 tree 轮询 → 流程图渲染八大节点
    │
    ▼
⑤ 进入「一、锁定目标」，按原门禁执行；SSE 继续吐进度，tree 点亮
```

**为什么不让模型自由规划八节点？**

- 模型漏写 / 改名 / 少一段 → 树与门禁对不上 → **卡死或甲方看到「假流程」**。  
- 固定模板 + Stream 念一遍，既有「规划感」，又和附录 C 门禁一致。

### D.4 Stream 与树如何「关联」（前端契约建议）

仅拼 `assistant.delta.content` **不够稳**（甲方要的是流程图跟着规划变）。建议增加**可忽略兼容**的结构化字段（自然语言照旧有）：

| SSE / 旁路事件 | 含义 | 前端动作 |
|----------------|------|----------|
| `plan.started` | 规划开始 | 流程图区显示「规划中…」骨架/转圈 |
| `plan.ready` | 规划完成 | payload 带 `phases: [{key,title,order}×8]`；拉/合并 tree，展示八大节点 |
| `gateStep` / `phaseKey` | 当前阶段 | 高亮对应 L1（见既有 P1 待办） |
| `assistant.delta` | 人话进度 | 思考区照常追加 |

`plan.ready` 的 phases 示例：

```json
{
  "eventType": "plan.ready",
  "taskId": "...",
  "phases": [
    { "phaseKey": "phase_lock_target", "title": "一、锁定目标", "order": 1 },
    { "phaseKey": "phase_discovery", "title": "二、线索发现", "order": 2 },
    { "phaseKey": "phase_account_collect", "title": "三、账号采集", "order": 3 },
    { "phaseKey": "phase_collision", "title": "四、关联碰撞", "order": 4 },
    { "phaseKey": "phase_content", "title": "五、内容采集", "order": 5 },
    { "phaseKey": "phase_assets", "title": "六、资产沉淀", "order": 6 },
    { "phaseKey": "phase_analysis", "title": "七、深度研判", "order": 7 },
    { "phaseKey": "phase_report", "title": "八、报告生成", "order": 8 }
  ]
}
```

思考区可见文案示例（可与事件同时发）：

```text
任务规划中…
已规划本任务执行节点：
① 锁定目标  ② 线索发现  ③ 账号采集  ④ 关联碰撞
⑤ 内容采集  ⑥ 资产沉淀  ⑦ 深度研判  ⑧ 报告生成
开始执行：一、锁定目标…
```

### D.5 三种实现档位（按投入）

| 档位 | 做法 | 体验 | 风险 |
|------|------|------|------|
| **L0 纯前端** | 起任务后前端本地先播「规划中」，再展示写死的八节点；Stream 仍是模型自由输出 | 快 | 文案与树可能不同步 |
| **L1 推荐** | Java 起任务插 `step_plan`；建任务后**服务端立刻** `plan.ready` + 插八 L1；Stream 注入固定规划文案（不必等模型） | 稳、像规划 | 低 |
| **L2 增强** | L1 + Agent 首轮必须 `finish step_plan`；允许在规划文案里带种子平台说明，但 **phases 列表仍以服务端模板为准** | 更「模型感」 | 中（要防模型不 finish） |

**04 建议默认 L1**：规划 ≤1 秒完成，不占用模型回合，避免「规划节点卡死」。

### D.6 和「展示树 / 执行树」怎么接

- `plan.ready` 挂出的是 **L1 八大展示父节点**（A 级壳）。  
- 其下仍挂现网 C 级 `step1`～`step11`（或投影映射，见正文各阶段表）。  
- **门禁不认「规划台词」**，只认附录 C 的执行 key。  
- `step_plan` 只表示「开场规划」；完成后不得再挡业务工具（与 05 终稿前 finish plan 类似，但 04 应在进 step1 前就 finish）。

### D.7 验收口径（给甲方演示）

1. 下发写报任务后，思考流先出现「任务规划中…」。  
2. 数秒内出现「已规划好」八节点清单（文案）。  
3. 流程图出现八个大节点（非 11 个技术标题）。  
4. 随后高亮「一、锁定目标」，开始种子采集；后续随 stream/tree 推进。  
5. 中断重连：靠 `GET /tree` 仍能看到八节点；不依赖只活在内存里的 SSE。
