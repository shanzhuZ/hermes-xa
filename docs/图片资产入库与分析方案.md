## 一、建设目标

当前 01～04 流程已经具备头像、封面、发文配图的采集及部分 OCR/Vision 能力，但图片本身、关联关系、处理状态和分析结果尚未形成统一的数据资产。

本方案建设一套独立图片处理能力：

1. 采集主页头像、主页封面和发文配图。
2. 原图下载后写入 HBase，避免 Instagram、Facebook 等平台 CDN 地址过期后无法查看。
3. MySQL 保存图片索引及业务关联：
   - `task_id`
   - 关联账号 ID
   - 关联发文 ID
   - 图片来源类型
   - HBase RowKey
   - 分析状态
   - OCR 文本
   - Vision 描述
   - 结构化分析 JSON
4. 图片分析结果同时服务：
   - 前端图片及分析结果展示
   - 后续 Skill、模型分析与画像写报
   - 检索、统计和报表
5. 前端统一通过 Java API 访问，禁止前端直连 HBase。

## 三、总体架构

```text
01～04 主流程
   │
   ├─ collect_profiles（头像、封面及主页原始数据）
   ├─ collect_posts（发文及媒体原始数据）
   │
   ▼
图片处理 Skill / scripts/image_pipeline
   ├─ 发现图片及关联对象
   ├─ requests 下载原图
   ├─ 计算 SHA-256
   ├─ 原图写入 HBase
   ├─ 元数据写入 MySQL collect_images
   ├─ 调用 OCR / Vision
   └─ 更新分析状态、文本及结构化 JSON
          │
          ├─ 后续 Skill / 模型读取
          └─ Java API 查询
                 ├─ 图片列表及分析结果
                 └─ 从 HBase 读取原图字节
                        ▼
                      前端
```

### 3.1 Python 侧职责

- 从 `collect_profiles`、`collect_posts` 及其 `raw_json` 发现图片。
- 使用 `requests` 下载图片，处理超时、重试、User-Agent、Referer 和响应类型校验。
- 计算图片哈希并进行幂等处理。
- 将原图写入 HBase。
- 将索引、关联关系和状态写入 MySQL。
- 调用现有 OCR/Vision 能力并保存结果。
- 对失败图片记录明确错误，支持后续重试。

### 3.2 Java 侧职责

- 查询 MySQL 图片列表及分析结果。
- 根据 `image_id` 查询 `hbase_row_key`。
- 从 HBase 读取原图字节。
- 根据 MIME 类型返回图片响应。
- 对不存在、未入 HBase、读取失败等情况返回明确 HTTP 状态。

### 3.3 前端职责

- 调用 Java API 获取图片列表。
- 展示图片来源、关联账号、关联发文和分析状态。
- 展示 OCR、Vision 文本及结构化分析结果。
- 使用 Java 提供的图片字节接口渲染原图。

## 四、MySQL 表设计

第一期新建一张核心表：`collect_images`。

```sql
CREATE TABLE IF NOT EXISTS collect_images (
    image_id           VARCHAR(64)   NOT NULL COMMENT '图片记录唯一ID',
    task_id            VARCHAR(64)   NOT NULL COMMENT '所属任务ID',
    task_type          VARCHAR(32)   NULL COMMENT '任务类型，便于按业务查询',
    source_type        VARCHAR(32)   NOT NULL COMMENT '来源：profile_avatar/profile_cover/post_media',
    platform           VARCHAR(32)   NULL COMMENT '来源平台',
    account_id         VARCHAR(128)  NULL COMMENT '关联账号ID',
    post_id            VARCHAR(128)  NULL COMMENT '关联发文ID，对应 collect_posts.content_id',
    profile_id         VARCHAR(128)  NULL COMMENT '关联主页ID，通常为 collect_profiles.account_id',
    origin_url         TEXT          NULL COMMENT '原始图片URL',
    hbase_row_key      VARCHAR(128)  NULL COMMENT 'HBase原图RowKey',
    content_sha256     CHAR(64)      NULL COMMENT '原图SHA-256，用于幂等和去重',
    mime_type          VARCHAR(64)   NULL COMMENT '图片MIME类型',
    file_size          BIGINT        NULL COMMENT '原图字节数',
    width              INT           NULL COMMENT '图片宽度',
    height             INT           NULL COMMENT '图片高度',
    storage_status     VARCHAR(16)   NOT NULL DEFAULT 'pending'
        COMMENT '存储状态：pending/downloading/stored/failed',
    analyze_status     VARCHAR(16)   NOT NULL DEFAULT 'pending'
        COMMENT '分析状态：pending/running/completed/failed/skipped',
    ocr_text           MEDIUMTEXT    NULL COMMENT 'OCR识别文本',
    vision_text        MEDIUMTEXT    NULL COMMENT 'Vision图片描述',
    analysis_json      JSON          NULL COMMENT '结构化分析结果',
    error_message      VARCHAR(1000) NULL COMMENT '最近一次失败原因',
    retry_count        INT           NOT NULL DEFAULT 0 COMMENT '处理重试次数',
    tool_output_id     BIGINT        NULL COMMENT '关联OCR/Vision工具输出ID',
    created_at         DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    updated_at         DATETIME(3)   NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
                                      ON UPDATE CURRENT_TIMESTAMP(3),
    stored_at          DATETIME(3)   NULL COMMENT '原图写入HBase时间',
    analyzed_at        DATETIME(3)   NULL COMMENT '分析完成时间',

    PRIMARY KEY (image_id),
    KEY idx_task (task_id),
    KEY idx_task_status (task_id, analyze_status),
    KEY idx_task_source (task_id, source_type),
    KEY idx_account (task_id, platform, account_id),
    KEY idx_post (task_id, platform, post_id),
    KEY idx_sha256 (content_sha256),
    KEY idx_storage_status (storage_status),
    CONSTRAINT fk_collect_images_task
        FOREIGN KEY (task_id) REFERENCES hermes_tasks(task_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4
  COMMENT='图片资产、业务关联及OCR/Vision分析结果';
```

### 4.1 字段说明

#### 图片来源类型

| `source_type` | 含义 |
|---------------|------|
| `profile_avatar` | 主页头像 |
| `profile_cover` | 主页封面 |
| `post_media` | 发文配图 |

#### 存储状态

```text
pending → downloading → stored
                    └→ failed
```

#### 分析状态

```text
pending → running → completed
                  ├→ failed
                  └→ skipped
```

存储状态与分析状态分开，避免“下载失败”和“OCR/Vision 失败”混为同一个状态。

### 4.2 幂等策略

第一期按“任务内图片记录”处理：

```text
image_id = UUID，或由 task_id + source_type + platform + account_id/post_id + URL 摘要稳定生成
```

建议添加业务幂等判断：

```text
task_id + source_type + platform + account_id + post_id + origin_url
```

下载后再计算 `content_sha256`。同一任务中相同哈希的原图只写一次 HBase，但可以根据实际业务保留多条关联记录。

第一期暂不拆成“全局图片表 + 图片关联表”，避免过度设计。数据量增大或跨任务复用需求明确后再拆。

## 五、HBase 表设计

建议表名：

```text
collect_image_bytes
```

### 5.1 RowKey

建议：

```text
img:{taskId}:{sha256前16位}
```

示例：

```text
img:9c863d2b-ef30-47ac-9f0d-066a41ded5df:a92fd43c1120bb48
```

当前单任务图片量较小，该 RowKey 足够使用。后续数据规模增大时，可在前面增加哈希盐值避免热点。

### 5.2 列族

第一期只使用一个列族 `cf`：

| 列 | 内容 |
|----|------|
| `cf:bytes` | 原图二进制 |
| `cf:mime` | MIME 类型 |
| `cf:url` | 原始 URL |
| `cf:sha256` | SHA-256 |
| `cf:file_size` | 文件大小 |
| `cf:created_at` | 写入时间 |

OCR、Vision 及结构化结果仍放 MySQL，便于检索、分页、筛选和前端展示。

## 六、Python 图片处理模块

建议目录：

```text
scripts/image_pipeline/
├── __init__.py
├── discover.py
├── downloader.py
├── hbase_store.py
├── mysql_store.py
├── analyzer.py
└── run.py
```

为了保持代码易读，每个文件只承担一个明确职责，不做复杂框架和过度方法拆分。

### 6.1 `discover.py`

负责发现图片及业务关系：

- `collect_profiles.avatar_url`
- 各平台主页封面字段
- `collect_profiles.raw_json`
- `collect_posts.media_json`
- `collect_posts.raw_json`

统一输出：

```python
{
    "task_id": "...",
    "task_type": "account_collect",
    "source_type": "post_media",
    "platform": "instagram",
    "account_id": "laowhy86",
    "profile_id": "laowhy86",
    "post_id": "Cwa4MLUP98T",
    "origin_url": "https://..."
}
```

各平台媒体字段解析集中在该模块，避免散落到 01～04 的 sink 中。

### 6.2 `downloader.py`

使用 `requests` 下载：

- 连接超时和读取超时分开设置。
- 设置浏览器 User-Agent。
- 必要时按平台补 Referer。
- 限制最大文件大小，避免误下载视频或超大文件。
- 校验 HTTP 状态、`Content-Type` 和文件头。
- CDN 失败时进行有限次数重试，禁止无限重试。
- 下载后计算 SHA-256。

### 6.3 `hbase_store.py`

根据 Java `HBaseConfig`（ZooKeeper）接入：

```text
hbase.zookeeper.quorum = 192.168.3.124
hbase.zookeeper.property.clientPort = 2181
```

- Java：`HBaseConfiguration` + `ConnectionFactory`（hp1 / cluster2）
- Python：Thrift + happybase（默认 `192.168.3.124:9090`，**不是** Master 端口 16000）
- 配置见 `.env`：`HERMES_HBASE_ZK` / `HERMES_HBASE_ZK_PORT` / `HERMES_HBASE_THRIFT_*`
- 表名默认 `collect_image_bytes`，列族 `cf`；`HERMES_HBASE_AUTO_CREATE_TABLE=1` 时可自动建表

HBase 密码、地址等配置放环境变量或项目配置文件，禁止硬编码进 Skill。

### 6.4 `mysql_store.py`

负责：

- 写入或更新 `collect_images`。
- 原图下载前写 `storage_status=downloading`。
- HBase 成功后写 `storage_status=stored`。
- 分析开始写 `analyze_status=running`。
- 分析成功写文本、JSON 和 `completed`。
- 失败写 `failed`、错误原因及重试次数。

### 6.5 `analyzer.py`

第一期与现有 OCR/Vision 并列：

- OCR 结果写 `ocr_text`。
- Vision 自然语言结果写 `vision_text`。
- 统一结构化结果写 `analysis_json`。

建议 `analysis_json` 第一版结构：

```json
{
  "summary": "图片整体描述",
  "imageType": "photo|screenshot|poster|meme|document|other",
  "languages": ["zh", "en"],
  "objects": ["人物", "手机", "建筑"],
  "persons": [
    {
      "description": "白人男性，短发",
      "isLikelyAccountOwner": true
    }
  ],
  "scene": "户外",
  "topics": ["中国", "科技"],
  "sensitiveSignals": [],
  "confidence": 0.92
}
```

结构第一期保持通用，不把特定业务判断写死。以后可通过 `analysis_version` 扩展版本控制；第一期如需要，可在 `analysis_json` 内增加版本字段。

### 6.6 `run.py`

提供可直接运行的入口：

```shell
python -m image_pipeline.run --task-id <taskId>
```

第一期支持：

- 按任务全量处理
- 失败重试
- 仅发现、不分析的诊断模式
- 输出处理总数、成功数、失败数

## 七、图片 Skill 设计

建议 Skill：

```text
skills/account-intelligence/image-asset-analysis/SKILL.md
```

Skill 负责流程编排，不直接保存数据库密码或复杂业务实现。

### 7.1 Skill 职责

1. 接收 `task_id`。
2. 运行图片发现与入库模块。
3. 检查 HBase/MySQL 落库结果。
4. 对待分析图片调用 OCR/Vision。
5. 更新分析结果。
6. 返回处理摘要供主流程继续使用。

### 7.2 返回摘要

```json
{
  "taskId": "...",
  "discovered": 20,
  "stored": 18,
  "analyzed": 17,
  "failed": 3,
  "profileImages": 4,
  "postImages": 16
}
```

### 7.3 与现有图片分析关系

第一期：

- 现有 OCR/Vision 继续运行。
- 新 Skill 独立保存图片资产和业务分析结果。
- 不修改已有图片流的状态机和完成条件。

后续：

1. 先让旧流程读取 `collect_images` 的分析结果，减少重复 Vision。
2. 再把旧图片流的下载与分析迁移到新模块。
3. 验证稳定后停用旧的重复图片处理代码。

```http

```

### 9.3 原图读取

```http
GET /api/images/{imageId}/bytes
```

处理流程：

1. 根据 `imageId` 查询 MySQL。
2. 校验 `storage_status=stored` 且 `hbase_row_key` 非空。
3. 调用 HBase 客户端读取 `cf:bytes`。
4. 使用 MySQL/HBase 中的 MIME 返回响应。
5. 支持浏览器缓存头和必要的内容长度。

异常约定：

| HTTP | 场景 |
|------|------|
| 404 | imageId 不存在或 HBase 无对应 RowKey |
| 409 | 图片仍在下载或未写入 HBase |
| 500 | HBase 读取异常 |

### 9.4 Java 代码可读性要求

- Controller 只负责参数校验和 HTTP 响应。
- Service 方法控制在少量核心方法：
  - `listTaskImages(...)`
  - `getImageDetail(...)`
  - `getImageBytes(...)`
- 不为简单字段映射创建大量小方法。
- HBase 连接、表名、列族等配置集中在一个客户端类中。
- 每个公开方法用中文注释说明：
  - 参数来源
  - 查询步骤
  - 返回内容
  - 失败场景

## 十、失败处理与重试

### 10.1 下载失败

- 记录 `storage_status=failed`。
- 保存 HTTP 状态、超时或类型不合法原因。
- `retry_count + 1`。
- 原始 URL 保留，允许后续重试。

### 10.2 HBase 写入失败

- 不得将 `storage_status` 标为 `stored`。
- MySQL 保留下载得到的哈希及错误原因。
- 避免 MySQL 显示可取图但 HBase 实际无数据。

### 10.3 OCR/Vision 失败

- 原图仍保留在 HBase。
- `storage_status` 继续为 `stored`。
- `analyze_status=failed`。
- 支持以后只重跑分析，无需重新下载。

### 10.4 幂等与重复执行

- 已 `stored` 且 RowKey 存在时，不重复写原图。
- 已 `completed` 时默认不重复分析。
- 手动指定 `--force-analyze` 时允许重新分析并覆盖结果。

## 十一、安全与限制

1. HBase 连接信息通过环境变量或配置文件注入。
2. Java API 不返回 HBase 地址和 RowKey 给前端，除非调试接口明确需要。
3. 原图接口需沿用项目现有鉴权策略；若当前无鉴权，至少限制任意 RowKey 查询，只允许通过 `imageId`。
4. 下载图片需限制最大大小，第一期建议 20 MB。
5. 必须校验 MIME 和文件头，防止将 HTML、视频或异常文件按图片入库。
6. OCR/Vision 的原始工具输出仍可保留在 `hermes_tool_outputs`，`collect_images` 保存业务可用结果。

## 十三、验收标准

### 13.1 数据正确性

- 头像、封面、发文配图能正确区分来源。
- 每条图片记录均有 `task_id`。
- 账号图片有 `account_id`。
- 发文配图有 `post_id`，且能关联对应发文。
- HBase RowKey 与 MySQL 一致。
- CDN 地址失效后仍能从 HBase 读取原图。

### 13.2 状态正确性

- 下载、HBase 写入、OCR、Vision 各阶段失败可区分。
- 失败后可以重试。
- 重复执行不会产生失控的重复数据。
- 主流程不因单张图片失败而整体失败。

### 13.3 分析结果

- OCR 文本可查询和展示。
- Vision 文本可查询和展示。
- `analysis_json` 格式稳定、可解析。
- 04 写报能够读取已完成图片分析结果。

### 13.4 Java API

- 列表支持分页和状态/来源筛选。
- 枚举展示值返回中文。
- 原图接口正确返回 MIME 和字节。
- 图片不存在、未存储和 HBase 异常有明确错误。
- Java 代码中文注释充分、方法数量适中、调用关系易懂。

## 十四、暂不实施内容

第一期明确不做：

- 视频原文件入 HBase。
- 视频转码、抽帧、音频识别和字幕分析。
- 图片处理消息队列。
- 大规模并发分析。
- 全局图片主表和多任务关联表拆分。
- 立即替换现有 OCR/Vision 状态机。

图片方案稳定后，视频可复用以下部分：

- MySQL 资产索引和业务关联模式。
- HBase 原文件存储。
- Java 统一字节流接口。
- Python 独立处理 Skill。
- 分析状态、重试和前端展示模式。

## 十六、最终实施原则

1. 第一阶段以“可用、稳定、可回放”为主，不追求过度抽象。
2. Python 集中处理图片资产，避免四类 sink 各写一套下载逻辑。
3. Java 统一对前端提供 API，不暴露 HBase。
4. 新图片 Skill 与旧 OCR/Vision 并列运行，稳定后再渐进替换。
5. 单图失败不拖垮主任务，所有失败必须可定位、可重试。
6. 未收到用户明确“开工”指令前，本方案只作为设计文档，不执行建表、建 HBase 表或代码实现。
